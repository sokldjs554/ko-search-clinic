# 아키텍처 상세

## 전체 흐름

```
[상품 카탈로그 72건] ──► [Kiwi 분석기 + 설정] ──► [BM25 역색인]
                              ▲                        │
              사용자 사전 · 동의어 · 분해 확장          │ search / grep / analyze
                              │                        ▼
[처방 Prescription] ──►  [회귀 게이트]  ◄──── [진료 도구 ClinicExecutor]
   (pydantic IR)        전체 평가셋 재실행            ▲ tool_use
                              │                        │
                    채택 │ 기각+회귀내역      [진료 루프] ◄─ LLMClient ─ Scripted / Claude
                              ▼
                 [설정 편입 + 패치 원장] ──► [ES nori 설정 렌더링]
```

## 계층별 설계

### 1. 분석 계층 (`analysis/`)

**config.py** — 패치가 누적되는 대상은 코드가 아니라 **설정**이다.
세 요소가 실제 한국어 검색 실패의 서로 다른 형태에 대응한다:

| 요소 | 고치는 실패 | Elasticsearch 대응물 |
|---|---|---|
| `UserWord` | 분석기가 단어를 부숨 (아답터→[아,답,터]) | `user_dictionary_rules` |
| `SynonymGroup` | 표기 변형·유의어 단절 (케잌↔케이크) | `synonym_graph` filter |
| `CompoundExpansion` | 복합어 통짜 (물티슈↛티슈) | 복합어 규칙 + `decompound_mode: mixed` |

설정은 pydantic으로 검증·직렬화되므로 버전 관리, 롤백, ES 렌더링이 전부
같은 타입 위에서 동작한다. `copy_with()`는 원본을 불변으로 두고 패치가
더해진 새 설정을 반환한다 — 롤백 = 원본을 계속 쓰기.

**analyzer.py** — 파이프라인:

```
원문 → Kiwi 형태소 분석 (사용자 사전 반영)
    → 내용어 필터 (N*/SL/SN/SH/XR/VV/VA — nori POS 필터와 같은 취지)
    → 소문자화
    → 복합어 분해 확장 (물티슈 → 물티슈·물·티슈, mixed 방식)
    → 동의어 정규화 (그룹 구성원 → 대표형)
```

색인과 질의가 같은 파이프라인을 지나므로 설정 변경 = 재색인이다.
ES에서 analyzer 변경 시 reindex가 필요한 것과 같은 제약을 일부러 유지했다.

`explain()`은 각 토큰이 나온 경로(kiwi / expansion / synonym:원형)를 남긴다 —
진단 도구가 이것을 그대로 노출해 의사의 증거가 된다.

**Kiwi 인스턴스 캐시** — 초기화가 ~2초라 게이트가 샌드박스를 만들 때마다
새로 초기화하면 진료 한 바퀴가 분 단위가 된다. tokenize는 인스턴스 상태를
바꾸지 않으므로 **등록 단어 집합이 같으면 같은 인스턴스를 공유**한다.
동의어·분해 확장은 Kiwi 밖(파이썬 후처리)에서 적용되므로 캐시 키에 안 들어간다.

**jamo.py** — 표기 변형 탐지의 기반. '케잌'과 '케이크'는 음절로는 완전히 다른
문자열이지만 자모로 풀면(ㅋㅔㅇㅣㅋ vs ㅋㅔㅇㅣㅋㅡ) 거의 같다. 유니코드 산술
(U+AC00 + 초성×588 + 중성×28 + 종성)로 외부 의존성 없이 구현했다.

### 2. 색인 계층 (`index/`)

**bm25.py** — Lucene 방식 BM25(k1=1.2, b=0.75, IDF=log(1+(N-df+0.5)/(df+0.5)))
직접 구현. 동점은 doc_id 사전순 — **랭킹의 결정성이 곧 채점의 결정성**이다.
패치 전후 비교가 평가의 핵심이므로 순위가 실행마다 흔들리면 안 된다.

**engine.py** — `with_config(config)`가 핵심이다. 같은 코퍼스에 다른 설정을
적용한 새 엔진(샌드박스)을 만든다. 게이트는 샌드박스에서 전수 검증하고,
채택 시 샌드박스를 현역으로 승격한다. `grep_raw()`는 분석기를 우회한 원문
부분 문자열 검색(공백 무시)으로, "검색 0건 vs 원문 존재"라는 진단의 결정적
증거를 만든다.

### 3. 코퍼스 계층 (`corpus/`)

문서 72건, 질의 36건(건강 20 + 실패 16)이 전부 **실측된 Kiwi 동작 위에
설계된 의도적 구조물**이다. 작성 전에 측정한 사실들:

- 표기 변형 8쌍(케이크/케잌 등)은 토큰이 완전히 단절된다
- 아답터는 [아, 답, 터]로 부서진다 (사전 등록 없이는 동의어도 무효)
- 물티슈·샤인머스캣은 한 토큰으로 유지된다 (부분어 질의가 0건이 되는 근거)
- 팬미팅·선풍기 문서는 '팬' 토큰을 가진다 (과잉 동의어 함정의 성립 근거)

관찰 하나를 기록해 둔다: Kiwi는 '바디워시'를 **문맥에 따라 다르게** 분석한다
(상품명 "퍼퓸 바디워시 대용량"에서는 [바디, 워시], 설명문에서는 통짜).
형태소 분석의 문맥 의존성이 만드는 비일관성의 실측 표본으로, 문서를 고쳐
숨기는 대신 그대로 두고 계약 테스트에 주석으로 남겼다.

설계 계약(예: '티슈'가 다른 문서에 단독 토큰으로 등장하면 안 된다)은
`tests/test_corpus_contract.py`가 상시 검증한다. 문서 하나를 무심코 고치면
실패 계열이 조용히 무너지기 때문이다.

### 4. 처방·게이트 계층 (`patch/`)

**ir.py** — 처방은 산문이 아니라 pydantic 모델이다. 빈 처방, 재구성 안 되는
분해 규칙(물+휴지≠물티슈), 중복 항목은 제출 시점에 거부된다. 하나의 처방이
여러 패치를 담을 수 있다 — 아답터처럼 사전 등록과 동의어가 **함께** 있어야만
동작하는 복합 처방이 실재하기 때문이다.

**gate.py** — 판정 규칙 (전부 만족해야 채택):

1. **표적 개선**: 표적 질의 nDCG가 +0.05 이상 오른다
2. **무회귀**: 다른 모든 질의에서 nDCG·recall·precision@5 하락이 ε(0.02) 이내
   (BM25는 문서빈도 변화로 점수가 미세하게 흔들리므로 0이 아니라 ε)
3. **전체 보존**: 평가셋 전체 평균 nDCG가 떨어지지 않는다

precision@5를 넣은 이유: nDCG는 정답 아래에 쌓이는 쓰레기를 벌하지 않는다.
과잉 동의어(프라이팬=팬)가 만드는 오염은 정답 순위를 크게 안 바꾸면서 상위
5건을 쓰레기로 채우는데, 그것을 precision@5가 잡는다 (`clinic demo-trap`).

기각은 실패가 아니라 **다음 처방의 입력**이다. 어떤 질의가 얼마나 나빠졌는지
(RegressionRecord)를 그대로 돌려줘 의사가 처방을 좁혀 재시도하게 한다.

**es_render.py** — 채택된 설정을 실제 ES nori 인덱스 설정 JSON으로 렌더링한다.
패치 유형 자체를 nori 설정과 1:1 대응하도록 설계했으므로 렌더링은 변환이
아니라 표기 변경에 가깝다.

### 5. 진료 계층 (`doctor/`)

**tools.py** — 도구 6종. 핵심 설계 두 가지:

1. **검증이 도구 안에 있다.** `submit_prescription`이 곧 게이트 실행이다.
   의사는 검증을 건너뛸 방법이 없다.
2. **의사에게 qrels(정답표)는 보이지 않는다.** 의사가 보는 것은 검색 결과,
   원문 grep, 형태소 분석, 자모 유사 토큰뿐이다. 정답표를 보면 진단이 아니라
   답 맞추기가 된다.

| 도구 | 역할 |
|---|---|
| `search_products` | 현재 설정 검색 + 매칭 토큰 |
| `grep_documents` | 분석기 우회 원문 검색 — "없는 문서 vs 못 찾는 문서" 구분 |
| `analyze_text` | 분석 파이프라인 토큰 + 경로 |
| `inspect_document` | 문서 원문 + 색인 토큰 |
| `find_similar_tokens` | 색인 어휘의 자모 유사 토큰 (표기 변형 상대 찾기) |
| `submit_prescription` | 처방 제출 = 게이트 실행 (종결 도구) |

**loop.py** — Messages API 규약을 정확히 따르는 수동 tool-use 루프.
assistant content 전체를 히스토리에 보존(thinking 포함)하고, 한 턴의 모든
tool_use에 하나의 user 메시지로 tool_result를 돌려준다. 기각 피드백은
tool_result로 돌아가 같은 대화 안에서 재처방을 유도한다 (최대 3회).

**scripted.py** — 결정적 베이스라인. R1(자모 유사도 ≥0.65 → 동의어),
R2(부분어 포함 → 분해 확장) 두 규칙만 갖는다. 임계값 0.65는 실측으로 정했다:
케잌↔케이크(0.67)는 잡고 핸드폰↔휴대폰(0.63)은 놓친다 — 이 경계선이
`tests/test_jamo.py`에 고정돼 있다. 이 베이스라인이 원리적으로 못 푸는
5건(영한 혼용·유의어·2단계 복합)이 LLM 의사의 가치를 측정 가능하게 만든다.

**llm.py** — LLMClient 프로토콜. AnthropicLLM은 `claude-opus-5`
(adaptive thinking 기본 — thinking 파라미터 미전송, 샘플링 파라미터 미사용),
`stop_reason == "refusal"` 명시 처리.

### 6. 평가 계층 (`evaluation/`)

치유율만 보면 "우연히 고침"과 "이해하고 고침"이 구분되지 않는다. 그래서
세 축으로 채점한다:

| 축 | 방식 | 잡는 실패 |
|---|---|---|
| 치유율 | 게이트 채택 여부 | 못 고침 |
| 진단 정확도 | 진단 계열 vs 정답 계열 라벨 | 고쳤지만 이유를 잘못 앎 (아답터 오진이 실례) |
| 처방 적합성 | 패치 유형 vs 정답 처방 유형 | 우연히 통하는 엉뚱한 처방 |

**ledger.py** — 채택된 모든 패치에 표적 질의·진단 근거·전후 지표를 기록한다.
운영 사전·동의어 파일이 "왜 넣었는지 아무도 모르는" 부채가 되는 것을 막는
장치이며, 나중에 항목을 의심할 때 근거를 재검증할 수 있다.
